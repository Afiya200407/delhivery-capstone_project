# Delhi Very Last-Mile Delay Intelligence Pipeline

## Project Overview

This project builds a reproducible shipment-delay intelligence
pipeline using synthetic logistics data.

The pipeline cleans shipment records, analyses delivery delays,
predicts delivery hours, classifies potentially delayed shipments,
segments delivery hubs, and generates operational recommendations.

## How to run

Run all commands from the repository root using Python 3.12.

For a fresh clone, install the dependencies and execute the scripts in this order:

```
pip install -r requirements.txt
python generate_data.py
python part_a_clean_eda.py
python part_b_regression.py
python part_c_classification.py
python part_d_segments.py
python package_model.py
python predict_delay.py
```

Model packaging: models/delay_model.pkl is regenerated by running python package_model.py. The committed pickle loads reliably only with the scikit-learn version pinned in requirements.txt.

## Model results (Regression)

1. **Baseline:** Predicting the training mean gives a validation R² of -0.0212 (RMSE 18.8552 hours).
  It explains none of the variation in delivery time, so every model has to beat it.

2. **Winner on validation:** Linear regression had the lowest validation RMSE, 4.8912 hours (R² 0.9313),
  just ahead of gradient boosting (4.9165 hours, R² 0.9306).

3. **Bias and variance:** At depth 1, train_rmse and val_rmse are both
  high and close together (11.6334 and 12.1324) same with the depths 2, 3 showing train_rmse and val_rmse (9.3687 and 10.4114) and (7.529 and 8.7033) respectively so the tree underfits (high bias). With no depth limit,
  train_rmse 0.0 but val_rmse is 7.789 as well as with the depths 8, 12 with train_rmse and val_rmse (3.336 and 6.8385) and (1.3613 and 7.4173) respectively so it overfits (high variance).
  The best depth was 6, with val_rmse 6.2796. 

4. **Learning rate:** 0.1 was best (R² 0.9306). 0.01 gave R² 0.7127: each tree corrects only 1% of the remaining
  error, so 100 trees are not enough to reach a good fit and the model underfits (too slow). 1.0 gave R² 0.8440: each tree applies the full correction, so the model overshoots and follows noise instead of settling on the best fit.

5. **Cross-validation:** The ranking disagrees with validation: gradient boosting scored
  0.9352 (std 0.0044) against 0.9261 (std 0.0048) for linear regression. I would ship Linear Regression because of the reason that Linear Regression performs almost as well as Gradient Boosting, with a cross-validation mean R² of 0.9261 compared to 0.9352 and nearly identical validation scores (0.9313 vs. 0.9306). It is also stable across folds, with a low CV standard deviation of 0.0048, easy to explain to planners because each feature has a clear effect, and inexpensive to retrain. Additionally, it achieves a strong test R² of 0.9493, making it a reliable and practical choice. Only this model was scored on the test set (RMSE 4.5235 hours, R² 0.9493), so there is no test figure for gradient boosting.

6. **Final test score:** Linear regression on the test rows: RMSE 4.5235 hours, R² 0.9493.

## Model Results (Classification)

1. **Blind Baseline:**
   The baseline achieved 76.67% accuracy by predicting every parcel as not delayed, but detected none of the 42 delayed parcels (recall = 0). This shows that accuracy alone is insufficient for evaluating a delay-detection model.

2. **Noise Columns:**
   Five bookkeeping columns contributed 22.44% of the Random Forest's total feature importance, yet ranked 8th, 12th, 14th, 16th, and 17th with F-score all below 5. This suggests the forest sometimes splits on noise, while F-scores help distinguish more informative features. Feature importance alone does not prove predictive signal.

3. **Feature Selection (k):**
   k = 7 performed best, with a validation F1 of 0.8333. The other values were 0.6988 (k = 5), 0.7857 (k = 10), 0.8049 (k = 12) and 0.7848 (k = 17).

4. **Hyperparameter Tuning:**
   The untuned Random Forest achieved the best validation F1 (0.8333), outperforming Grid Search (0.7750) and Randomized Search (0.7848), despite Grid Search having the best CV accuracy (0.8952). With only 180 validation samples, small metric differences can be unstable, so over-tuning to one validation split should be avoided.

5. **Threshold Selection:**
   A threshold of 0.5 was selected because it achieved 0.8333 recall while maintaining precision of 0.7955. At 0.6, precision increased to 0.8889, but recall fell to 0.7619, below the 0.80 target. At 0.4, recall increased to 0.8810, but precision dropped to 0.7400.

6. **Final Test Results:**
   At the selected threshold of 0.5, the model achieved precision = 0.6889, recall = 0.7561, and F1 = 0.7209. Test recall was below the 0.80 target and lower than validation recall (0.8333). With only 41 delayed test parcels, each outcome changes recall by approximately 2.4 percentage points. This difference may partly reflect sampling variability; the test results should be reported transparently, without retuning on the test set.

2. Tier Labels vs Actual Behaviour

The tier-versus-segment comparison identified four mismatches:

- HUB07 – Kolkata: Tier 1, but behaves like Watch.
- HUB13 – Nagpur: Tier 2, but behaves like Escalate.
- HUB15 – Kochi: Tier 2, but behaves like Escalate.
- HUB22 – Dehradun: Tier 3, but behaves like Watch.

These mismatches show that tier labels alone are not reliable indicators of operational behaviour. Hub segments should guide operational decisions.

3. Parcel Alert Threshold

A classification threshold of 0.5 is recommended for flagging potentially delayed parcels.

Based on the final test results:

- Precision of 0.6889 means approximately 7 out of every 10 flagged parcels are actually delayed.
- Recall of 0.7561 means approximately 7.6 out of every 10 delayed parcels are detected.

4. New Shipment Predictions

Out of the 48 new parcels:

- 8 parcels were flagged as potentially delayed.
- 6 parcels require hub-manager escalation.

These flagged shipments should receive proactive attention to reduce the risk of late delivery.

5. Why Three Hub Segments (K = 3)?

Although the clustering ratio increased for K = 4 (6.3047) and K = 5 (6.8866), these solutions produced very small clusters. K = 4 included clusters of 5 and 4 hubs, while K = 5 included clusters of 4, 3 and 2 hubs, both containing fewer than 6 hubs which is too small to carry its own playbook.

Since operations uses exactly three playbooks — Standard, Watch and Escalate — K = 3 provides more practical and actionable hub segments.

## Production Plan

1. Production Characteristics

Characteristic | Implementation in This Project |
|---|:---|
|Accuracy | Evaluated using test metrics in part_b_metrics.csv and part_c_final_test.csv.|
|Reliability | clean_shipments() handles duplicates, missing values and the 999-kg sentinel. A model reload check verifies that the saved pickle works.|
|Reproducibility | Pinned dependencies, fixed random_state values, a committed data generator and documented execution order.|
|Maintainability | Shared preprocessing functions in src/shipment_prep.py, separate scripts for each project part and configuration stored in CSV files.|
|Consistency| predict_delay.py reuses the same preprocessing functions, stored medians and feature_order.csv.|
|Monitorability | Weekly delayed share, flagged share and recall are tracked against defined thresholds.|
|Performance | Random Forest uses seven selected features, keeping the model input relatively compact. No specific prediction-speed claim is made without measurement.|

2. Monitoring Metrics and Triggers

The following are proposed operational monitoring rules:

| Metric | Baseline | Alert Trigger |
|---|---:|---|
| Weekly delayed share | 0.2317 (23.17%) | Changes by more than 5 percentage points for two consecutive weeks.|
| Weekly flagged share | Approximately 0.244 (24.44%) on validation | Falls outside a proposed 15%–35% monitoring band.|
| Recall on parcels with known outcomes | 0.8333 validation; 0.7561 test | Falls below 0.65 over four weeks, with at least 50 delayed parcels.|           

The flagged-share baseline of 0.244 is the share of validation rows flagged at threshold 0.5:
TP 35 + FP 9 = 44 of 180 rows, from `outputs/part_c_thresholds.csv`.

These thresholds are proposed monitoring choices and should be reviewed as real operational data becomes available.

3. Retraining and Drift Monitoring

- Retraining schedule: Retrain the models monthly, with an additional retraining review whenever a monitoring trigger is reached.
- Sale-event monitoring: The 15–28 September sale period should be compared with the previous comparable sale event rather than ordinary weeks, because sale periods can change shipment behaviour. Compare delay rates for sale_event_flag = 1 and sale_event_flag = 0 as an initial analysis.
- Data drift indicators: Monitor increases in delayed shipment share, changes in distance and stop-count distributions, hubs moving between segments, and changes in flagged share or recall compared with validation results.

## Limitations

1. Synthetic dataset: The project uses synthetic shipment data, so actual delivery behaviour may differ from the observed patterns.

2. Small test sample: The test set contains only 41 delayed parcels. The recall of 0.7561 is therefore uncertain, with each parcel changing recall by approximately 2.4 percentage points.

3. Validation-based threshold: The 0.5 threshold was selected using a single 180-row validation split containing 42 delayed parcels. Its performance may differ on other datasets.

4. Limited hub sample: Hub segmentation is based on only 24 hubs, with 50 parcels per hub.

5. Limited operational inputs: The model uses dispatch-time information and does not include live traffic or weather conditions.

Despite these limitations, the project demonstrates an end-to-end workflow for shipment data preparation, delay prediction, hub segmentation and operational decision support.
